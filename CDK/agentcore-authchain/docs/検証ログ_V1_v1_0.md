### 実測と解釈
- **［実測］本番PJ質問 #2 の証拠**：Cognito の**アクセストークンにはユーザー属性（`custom:*`）が載らない**。ID トークンには載る。AgentCore に渡すのはアクセストークン（仮決め #1）なので、**属性ベースの認可根拠をアクセストークンに載せるには Pre Token Gen（V2_0）が必須**——V1c の存在理由が実測で裏付けられた
- **［実測］名前空間の扱い**：Entra で Namespace 空にした追加クレームは **短名（`companyname`）で出る**（ランブックの推定が確定）。既定クレームは URI 形。Cognito 側マッピングのキーは短名で一致
- **［実測］Entra は値が空・未設定のクレームを SAML に含めない**。初回はクレーム未設定だったため属性が 1 つも来ず、Cognito は必須属性なしのためログインを成功させた（トークンは出るが属性なし）→ 「認証は通るが認可の根拠が無い」状態を実地で観測。切り分けの順序（トークン → `admin-get-user` → SAMLResponse）がそのまま効いた
- **［実測］Entra の署名は Assertion 側**（Response は未署名）。NameID は UPN・Format emailAddress（Cognito 公式は「不変の値を」と要求。UPN 変更に弱い点は本番の論点：objectid/pairwiseid）
- **［実測］** フェデレーションユーザーは自動グループ `<PoolId>_EntraID` に入り `cognito:groups` として**両トークン**に載る。IdP 由来を示す手掛かりになるが、認可には使わない（Cedar は `company_code` を見る）
- **［実測］** IdP 追加は「IdP 1 件＋クライアントの許可リスト 1 点」で完結。プール本体・ユーザーは無変更
- **［実測］** Cognito は URL メタデータから SSO エンドポイントを自動導出（証明書の手動登録不要）。メタデータ内の署名証明書 3 本は Cognito 公式のとおり「いずれかに一致すれば有効」
- **［判断］** メタデータ URL（テナント ID・アプリ ID 入り）は `-c samlMetadataUrl` で渡し、未指定時は synth で停止させる（意図せず IdP を消す UPDATE を防ぐ）。クレーム名も `-c` で上書き可能にし、Entra の実物と食い違ったときの再デプロイを容易にした
- **［設計］** `get_token.py` は 6 ステップ表示（設定／PKCE／authorize URL／callback／トークン交換／保存＋デコード）。`--idp EntraID` で hosted UI 選択画面を飛ばせる、`--manual` で callback 貼り付け対応

### 目的
Pre Token Generation（V2_0）を接続し、V1b の素トークンとの差分＝「トリガーが何をしたか」を見る。壊す実験（認可マスタから会社行を一時削除）で fail-closed（未ヒット→非注入＋WARNING）を実測する。

### 実測と解釈
- **［実測］トリガーの仕事＝トークンへの注入だけ**：before/after の差分は `company_code`／`department_code` の 2 クレーム（ID・アクセス両方）のみ。プロファイル（`admin-get-user`）は不変。「認可の根拠はトークンで運ぶ」の実証
- **［実測］本番PJ質問 #2 の補強**：V1b で「アクセストークンには属性が載らない」を見た上で、V2_0 の Pre Token Gen で **アクセストークンに正規化クレームを載せられる**ことを確認。AgentCore（V2〜V4）はこのアクセストークンで動く
- **［実測］fail-closed（仮決め #5）**：マスタ未登録の値は**クレーム単位で**注入されず WARNING。認証は成功しトークンは発行される（拒否は Cedar のデフォルト拒否に委ねる設計）。生値 `custom:company_raw` は ID トークンに残るため、「生値はあるが正規化コードが無い」状態を下流が区別できる
- **［実測］Lambda に渡る属性**：`custom:*_raw` は `request.userAttributes` に `custom:` プレフィックス付きで来る。`identities`（JSON 文字列）と `cognito:user_status`（EXTERNAL_PROVIDER）も来る
- **［実測］** `LambdaConfig` に旧フィールド `PreTokenGeneration` も同 ARN で自動設定される（CDK ドキュメントの「両方設定する場合は同一 ARN」の背景）
- **［推定→今後］** `TokenGeneration_RefreshTokens` でも同じ Lambda が走るはず（公式）→ マスタ変更は次のリフレッシュから反映。余力枠で refresh_token を使った再発行で確認可能
