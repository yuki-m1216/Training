# 整理：トークンの期限と失効 — JWT 方式で「権限の変更がいつ効くか」 v1.0

対象：V2 完了後の質疑（2026-09-06）を、この検証に限らず使える知識として整理したもの。実測は `検証ログ_V2_v1_0.md`（壊す実験・refresh の副産物）に基づく。事実（公式・実測）と［推定］を分ける。

## 0. 一枚で
- Runtime の入口認証は **JWT（Bearer）**。Runtime は**署名と中身**だけを見て門を開け、Cognito にも DynamoDB にも問い合わせない
- だから**発行済みのアクセストークンは期限まで有効**。マスタを直しても、Cognito 側で失効させても、Runtime には届かない
- 権限の変更が効く速さは **アクセストークンの寿命**で決まり、再認証を強制できる上限は **更新トークンの寿命**で決まる
- 個人を**即時**に止める弁は、トークンではなく呼び出しごとに評価される層（Gateway Policy の forbid。V4 で実測予定）

## 1. Runtime の入口認証（IAM ではなく JWT を選んだ理由と、今の検証内容）
| 方式 | 呼び手 | 呼び方 | ユーザー属性 |
|---|---|---|---|
| IAM（既定） | AWS 認証情報を持つ主体 | SDK `invoke_agent_runtime`（SigV4） | 届かない |
| **JWT（本検証）** | IdP 発行のトークンを持つ人 | HTTPS 直接、`Authorization: Bearer` | クレームとして届く |

両者は排他。`company_code`／`agents` で許可を決めたいので JWT（要件固有）。Runtime がコードに渡す前に検証するのは 4 段で、すべて **401**（実測、V2b）。

| 段 | 見るもの | 落ちたときの文言（実測） |
|---|---|---|
| 署名 | `discoveryUrl` → JWKS、`kid` で鍵選択、RS256 | "Invalid Signature for bearerToken" |
| 発行者・期限 | `iss`、`exp` | "Token has expired" |
| `client_id` | `allowedClients` | "Claim 'client_id' value mismatch with configuration."（ID トークンは `aud` しか無く落ちる） |
| `customClaims` | `agents` CONTAINS `inspect-headers` | "Authorization denied"（クレーム名を伏せる） |

未設定：`allowedAudience`（Cognito アクセストークンに `aud` 無し）、`allowedScopes`。本番案は `整理_システム全体像` §5-(b)。

## 2. 4 つの期限（Cognito アプリクライアント。本検証はすべて既定値）
| 項目 | 既定 | 何の期限か | 本検証での対応 |
|---|---|---|---|
| アクセストークン | 1 時間（5 分〜24 時間） | API に見せる「許可証」の寿命（`exp`） | 権限変更が効くまでの**最長の窓** |
| ID トークン | 1 時間（5 分〜24 時間） | 「誰か」をアプリに伝えるトークン。API には見せない | Runtime に送ると `client_id` 不一致で 401 |
| 更新トークン | 30 日（60 分〜10 年） | **再認証なし**で上 2 つを再発行できる期間。不透明文字列、Cognito 側に状態あり | refresh グラントで新アクセストークンを取得（実測） |
| 認証フローセッション | 3 分（3〜15 分） | ログイン**途中**（challenge の連鎖）の持ち時間 | 認可コードは別で 60 秒以内に交換 |

**更新トークンの期限は最初のログインからの絶対期限**。refresh を実行しても延びない。実測：refresh 応答に `refresh_token` は含まれず（ローテーション無効が既定）、同じ更新トークンを使い続ける。ローテーションを有効にした場合に期限がどうなるかは未確認［推定：元の期限を引き継ぐ］。

## 3. 「更新トークン」は何を守っているか（一般論）
アクセストークンが切れると refresh が走る、という連鎖は更新トークンが生きている間だけ回る。更新トークンの期限は**その連鎖を止める**ためにある。
1. **再認証の強制**：refresh は Cognito 内で完結し、IdP（Entra）には行かない。「遅くとも 30 日に一度は Entra を通す」を保証するのがこの期限
2. **盗まれたときの被害の上限**：アクセストークンの漏洩は寿命で無価値になるが、更新トークンの漏洩は期限まで新しいアクセストークンを作り続けられる。更新トークンの方が重い秘密（`out/` を 0600 にしている理由）
3. **放置セッションの掃除**：使われない端末・スクリプトのログイン状態をいつか切る

数字の決め方：短い refresh（8 時間〜1 日）は毎朝ログインする社内システム向け、長い refresh（30 日〜）はモバイル向け。どちらでも**アクセストークンは短く**が基本（refresh を長くしても権限変更の反映速度は落ちない）。

## 4. refresh で「最新になるもの」と「ならないもの」
refresh のたびに Pre Token Gen が走り（`triggerSource: TokenGeneration_RefreshTokens`、実測）、DynamoDB を引き直す。**refresh が古い情報を返すのではなく、発行済みトークンがスナップショットである**ことが遅延の正体。

| 変更 | 反映されるタイミング | 根拠 |
|---|---|---|
| DynamoDB マスタ（正規化、`AgentEntitlement`） | 次の refresh（上限＝アクセストークン寿命） | 実測（行削除 → refresh で `agents` 非注入） |
| Entra 側の属性（部署異動など） | 次の **Entra 経由の再ログイン**。refresh では保存済み `custom:*_raw` のまま Lambda が走る | ［推定］一般的な Cognito の挙動。V3/V4 で実測候補 |
| Entra でユーザー無効化 | 同上。更新トークンが生きている間（最長 30 日）は refresh が通る | ［推定］同上 |

最後の行が運用上の急所。IdP 側の退職処理だけでは足りず、Cognito 側の無効化（`admin-disable-user`、SCIM 等）か、更新トークン寿命の短縮を組み合わせる。

## 5. 緊急時（許可してはいけない人が通っている）の手段
| 手段 | 効き始め | 範囲 | 備考 |
|---|---|---|---|
| マスタを直す | 次の refresh（最長＝アクセストークン寿命） | 本人 | 恒久対応。実測 |
| Cognito で無効化／全端末サインアウト（`admin-user-global-sign-out`、`revoke-token`） | refresh は即停止。**発行済みアクセストークンは期限まで有効** | 本人 | Runtime は Cognito の失効状態を見ない（JWKS 検証のみ） |
| アクセストークン寿命を短くする（最短 5 分） | 以後の発行分から | 全員 | 予防。窓を 60 分 → 5 分に |
| Runtime の `customClaims` の一致値を変える（Lambda 側も） | deploy 完了で即時（今回 27 秒） | そのエージェントの全員 | 正しい人も再 refresh が必要 |
| アプリクライアント差し替え | 即時 | 全員 | 最終手段 |
| **Gateway Policy で本人を forbid**（`sub`／`upn`） | 次のツール呼び出しから即時 | 本人 | 呼び出しごとに評価。**個人単位の即時遮断の現実的な弁**。V4 で「有効なトークンのまま拒否される」を実測する |
| 実行時にマスタを照会する（計画書 §2-3 B 案） | 即時 | 本人 | 設計変更（呼び出しごとに DynamoDB） |

推奨の組み合わせ：**短いアクセストークン（予防）＋ Policy の forbid（緊急）＋ マスタ修正（恒久）**。順番は「Policy で止める → マスタを直す → 対象者に再ログインしてもらう」。

## 6. この検証への当てはめと、次の V で実測すること
- 現状：すべて既定値（access 1h／refresh 30 日）、取り消し有効、ローテーション無効。`identity-stack.ts` の `UserPoolClient` に `accessTokenValidity`／`idTokenValidity`／`refreshTokenValidity` を足せば変えられる（未変更）
- V4 で足す壊す実験：(1) 正しいトークンで 200 → Policy に forbid 追加 → **同じトークン**で拒否、(2) アクセストークン 5 分で反映が早まる
- V3/V4 で足す実測候補：Entra 側の属性変更が refresh では反映されず再ログインで反映される

## 7. ユースケース別の目安（理由付き。公式の推奨値ではなく設計の考え方）
値を決める順番は (1) **何が正本で、変更がどこで効くか**（§4）→ (2) 更新トークン＝再認証の上限 → (3) アクセストークン＝マスタ変更の反映速度、の順。数字より理由を持ち帰る。

| ユースケース | アクセス | 更新 | 理由 |
|---|---|---|---|
| **本検証の要件**（Entra 正本の部署でエージェント許可。異動は日付で切り替わる） | **15 分** | **8〜12 時間（1 営業日）** | 部署は Entra 属性なので**再ログインでしか反映されない** → 更新トークンが「異動が効くまでの上限」。翌朝のログインで新部署になれば業務上十分。Entra の SSO セッションが生きていれば再ログインは無言のリダイレクトで済む。アクセス 15 分は DynamoDB 側の許可変更の反映速度と、refresh ごとに Lambda が走る負荷の折り合い |
| 同上で、人事マスタ同期の DynamoDB を正本にした場合 | 15 分 | 7〜30 日 | 部署も `agents` も refresh で反映されるので、更新トークンは「再認証の頻度」だけを決めればよい。長くしても権限の反映は遅れない |
| 社内業務 Web（SSO、PC） | 15〜60 分 | 8〜24 時間 | 出社単位で再認証するのが自然。端末は管理下で盗難リスクが低め。IdP 側の無効化を翌日までに効かせたい |
| モバイルアプリ（BtoC） | 60 分 | 30〜90 日 | 毎日ログインさせると離脱する。端末に更新トークンが長く残るので**ローテーション＋再利用検知**と、サーバ側の失効（取り消し）を必ず組み合わせる |
| 高機密（管理コンソール、金融、個人情報の一括操作） | 5〜15 分 | 1〜8 時間、または更新トークン無し | 「切れたら都度認証」を許容する。更新トークン無しなら漏洩時の被害はアクセストークン寿命で頭打ち。MFA を再認証ごとに要求できる |
| M2M／バッチ（`client_credentials`） | 60 分 | 無し（更新トークンは発行されない） | 人がいないので再認証の概念が無く、シークレット自体が長期の秘密。**シークレットのローテーション**と最小スコープが対策の本体。兄弟プロジェクトの M2M クライアントがこの型 |
| エージェントの Runtime → Gateway 透過（本検証の V3） | 呼び元と同じ | 呼び元と同じ | 同じトークンを使い回すので、**呼び元の寿命がそのまま Gateway 側の上限**。長い処理の途中で切れると Gateway が 401 を返す（V3 の壊す実験）。本番は `aud` 絞りか OBO 交換（計画書 §3-5） |
| 開発・検証環境 | 60 分 | 1〜7 日 | 手戻りを減らす方が価値が高い。ただし本番値との差を docs に明記し、本番前に戻す（本検証は既定値のまま＝この行） |

共通の考え方：
- **アクセストークンを長くする理由はほぼ無い**。短くして困るのは refresh の頻度（IdP の負荷・Lambda の実行回数）だけで、5〜60 分の範囲で調整する
- **更新トークンは「誰の変更を、いつまでに効かせたいか」で決める**。IdP 側の変更（無効化・属性）が効くのはここが上限
- 長い更新トークンを選ぶなら、**ローテーション・取り消し・端末側の安全な保管**をセットにする。短い更新トークンを選ぶなら、**IdP の SSO セッション**で再ログインの体感を軽くする
- 即時性が要る場面（退職、漏洩、誤許可）はトークンの寿命では解けない。**呼び出しごとに評価される層**（Policy、実行時照会）と**サーバ側の失効**を別に持つ
