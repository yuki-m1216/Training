# docs 索引 — 何をどの順に読むか v1.0

作成日：2026-08-30。`CDK/agentcore-authchain/docs/` の文書一覧と役割。再開時は §1 の順に読む。各文書は末尾に「変更履歴」を持ち、追記式で育てる。

## 0. このプロジェクトの目的（2026-08-30 ユーザー訂正を反映）
目的は 2 軸ある。文書を読むとき・設計判断を記録するとき、どちらの軸の話かを意識する。
1. **要件固有の検証**：組織属性の正規化（DynamoDB 正規化マップ）→ エージェント認可マスタ（`AgentEntitlement` → `agents` クレーム）→ Runtime のカスタムクレーム認証 → 同一 Bearer の透過 → Gateway Policy（Cedar）。これは「盛り込んだ仕様」で、本番設計書の未確定事項を実測で埋める
2. **AgentCore を使った AI エージェントシステム全体を作り、理解する**：Runtime／Gateway／Identity／Policy／Observability の組み合わせ方を手を動かして学ぶ。**要件固有でない部分は公式のベストプラクティスに沿った形で作る**。検証の都合で緩めた箇所（DESTROY、PUBLIC、直接コードデプロイ、同一トークン透過など）は「検証用の簡略化」と明記し、本番案を併記する

## 2. 文書の分類
### 2-1 計画・台帳（設計判断が載る）

### 2-2 検証ログ（時系列の実測。予想 → 実測 → 解釈）
- `検証ログ_V0_v1_0.md` — 環境・前提（リージョン確定、arm64、CDK 版固定）
- `検証ログ_V1_v1_0.md` — Cognito（SP）＋ SAML IdP ＋ Pre Token Gen。V1 完了サマリと SAML 版シーケンス図

### 2-3 整理（概念・構成の理解。読み物）
- `整理_Cognito全体像_v1_0.md` — ユーザープールの構成要素と CDK 行・コンソール・実測の対応。落とし穴（§4）
- `整理_SAMLとOIDC_v1_0.md` — 両方式の比較（実測ベース）と「OIDC が主流」の背景（裏取り済み）

## 4. 書き方の約束（全文書共通）
- 公開リポジトリのため、GUID／アカウント ID／PoolId／ClientId／メール／UPN／トークン／鍵は `<tenant>`／`<ACCOUNT>`／`<PoolId>`／`<ClientId>`／`<user>@<tenant>…` にマスクする（コミット前に追加行をスキャン）
- 「予想 → 実測 → 解釈」の順で書き、**事実**（公式・実測）と **推定** を分ける。公式に無いものは［推定］を付ける
- ファイル名の `v1_0` は文書のメジャー版。中身の追記は「変更履歴」に日付付きで残す（ファイル名は変えない）
- 図は Mermaid（Claude が作図）。シーケンス図は各 V の完了サマリに置く
