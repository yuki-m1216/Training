- **［実測］この WSL は「Docker Desktop の統合の名残」＋「ネイティブ docker-ce」の混在環境**。3 つのつまずきはすべてこれが原因：

  3. QEMU ハンドラは Desktop 側ディストロの登録が一時的に見えていただけで、ネイティブ engine から当てにできない
- **［判断］回避策はユーザー設定を変えずに閉じた**：一時 `DOCKER_CONFIG` ディレクトリ（`config.json` = `{}`、`cli-plugins/docker-buildx` → docker-ce 版へのシンボリックリンク）＋ `tonistiigi/binfmt --install arm64`（`--privileged`。`qemu-aarch64` を F フラグで登録。**WSL 再起動（`wsl --shutdown`）で消える**ので都度再登録。`--uninstall arm64` で戻せる）
- **［決定（2026-08-16、ユーザー承認）］V2 の Runtime デプロイは「直接コードデプロイ（`AgentRuntimeArtifact.fromCodeAsset`、Docker 不要）」に変更**。プロンプト §4 V2／§5 の「DockerImageAsset／Dockerfile」からの逸脱として §0-1 規約 7 に従い相談し、承認を得た（仮決め事項表 #13）。理由：本検証の観測対象（JWT 認可・`requestHeaderAllowlist`・トークン中継）は Runtime リソース側の設定でパッケージング方式に依存しない（推定。V2 着手前に CDK API リファレンスで `Runtime` のプロパティを確認）／兄弟プロジェクトに実績あり／本環境の Docker 混在問題（上記 3 点）を丸ごと回避できる
  - 直接コードデプロイでも **依存パッケージは arm64（aarch64-manylinux2014）向け**にそろえる必要がある → 兄弟プロジェクトの `runtime-code/build.sh` 方式（`uv pip install --python-platform aarch64-manylinux2014 --python-version 3.13 --only-binary=:all:`）を流用。QEMU 不要
  - 本 TODO 3 の実測（buildx／QEMU）は「必要になった場合の手順と回避策」として残す。V2 では使わない
  - 参考として残す旧選択肢：(A) `DOCKER_CONFIG` 専用ディレクトリ／(B) `~/.docker/config.json` 修正（要相談）／(C) 多段ビルド＋uv で QEMU 非依存
- **［後始末］** 検証イメージ `authchain-arm64-check` 削除済み。`tonistiigi/binfmt:latest`（85MB）は再登録用に残置。ビルドキャッシュに python:3.12-slim(arm64) のレイヤが残る（V2 で再利用）

`decode_saml.py`（合成 SAMLResponse、POST バインディング）：`[HTTP-POST(base64 のみ)]` と判別。Response の id／destination／issuer（`sts.windows.net/<tenant>/`）／status（Success）／encrypted_assertion=False、Assertion の name_id＋format／subject_confirmation（Recipient＝`.../saml2/idpresponse`）／conditions／audience（`urn:amazon:cognito:sp:<PoolId>`）／authn_context、**Attributes の現物**（`http://schemas.xmlsoap.org/ws/2005/05/identity/claims/companyname = 株式会社テスト商事` 等）
`decode_saml.py`（合成 SAMLRequest、`SAMLRequest=...&RelayState=...` を丸ごと貼付）：`[HTTP-Redirect(base64 + raw DEFLATE)]` と判別。issuer（`urn:amazon:cognito:sp:<PoolId>`）／destination（`login.microsoftonline.com/<tenant>/saml2`）／AssertionConsumerServiceURL／ProtocolBinding（HTTP-POST）／NameIDPolicy Format

### 実測と解釈
- **［実測］** 2 本とも合成データで期待どおり動作。V1b でブラウザ DevTools から採った実物を通す準備が整った
- **［設計］** `decode_saml.py` は入力の種類を自動判別：base64 を解いて `<` で始まれば POST バインディング（SAMLResponse）、そうでなければ raw DEFLATE（wbits=-15）で展開して Redirect バインディング（SAMLRequest）。`%` を含めば URL デコード、`SAMLRequest=...&RelayState=...` 丸ごとにも対応（DevTools からのコピー事情に合わせた）。EncryptedAssertion の場合は「属性は見えない」旨を表示（Entra 側でトークン暗号化を有効にすると属性観測ができなくなることの気づきポイント）
- **［設計］** `decode_jwt.py --mask` は §6 のマスク規約（`sub`・メール等）を機械的に適用し、検証ログにそのまま貼れる出力にする。`custom:*` や注入クレーム、`token_use`／`scope`／`client_id` は観測対象なので触らない
- **［判断］** ユーザー指示により、本プロジェクトではテストを書かない（学び優先。グローバルの TDD 既定は本プロジェクトでは適用外）。先行して作成していた `scripts/tests/`（pytest 31 件合格）は削除済み。動作確認は合成データでの CLI 実行 1 回ずつに留めた
- **［推定］** Entra のクレーム名は「名前空間 URI ＋ 名前」（例 `http://schemas.xmlsoap.org/ws/2005/05/identity/claims/companyname`）が既定。名前空間を空にすると短名（`companyname`）で出る想定。どちらの形で出るかは V1b の実物で確定し、Cognito 側の属性マッピングのキーに使う（ランブックの該当手順を参照）
