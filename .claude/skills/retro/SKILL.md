PR のレビューコメントを振り返り、作業プロセスやスキル・ルールの改善案を検討します。

- 引数に PR 番号が指定された場合: その PR を対象にする
- 引数なしの場合: 直近のマージ済み PR を対象にする

## 手順

### 1. 対象 PR の特定

- 引数ありの場合: `gh pr view <number> --json number,title,state,mergedAt`
- 引数なしの場合: `gh pr list --state merged --limit 5 --json number,title,mergedAt` で直近の PR を一覧表示し、ユーザーにどの PR を振り返るか確認する

### 2. レビューコメントの収集

- `gh api --paginate /repos/:owner/:repo/pulls/<number>/comments` でファイル単位のレビューコメントを取得（ページネーション対応で全件取得）
- `gh pr view <number> --comments` で PR 全体へのコメントも確認
- ファイル単位のレビューコメントと PR 全体へのコメントをあわせて、レビュー関連のコメントが1件もない場合は「レビューコメントはありませんでした」と報告して終了

### 3. コメントの分類と分析

各コメントを以下の観点で分類する:

- **修正指摘**: コードやファイルの具体的な問題点（フォーマット、バージョン指定、設定ミス等）
- **設計・方針の指摘**: アプローチや設計判断に対するフィードバック
- **質問・確認**: 意図や背景の確認

分類後、以下を分析する:

- 指摘の根本原因は何か（知識不足、手順の抜け、検証不足 等）
- 同種の指摘が繰り返されていないか
- 既存のスキルやルールでカバーできていたはずの指摘はないか

### 4. 改善案の提示

分析結果をもとに、以下の改善先ごとに提案を整理してユーザーに提示する:

- **スキルの改善**: 既存スキルへの手順追加・修正（対象スキルとファイルパスを明示）
- **CLAUDE.md の改善**: プロジェクト全体に適用すべきルールの追加・修正
- **新規スキルの作成**: 既存スキルではカバーできない新しいワークフローの提案

提案は以下の形式で報告する:

```
### 改善案

#### 1. [改善先: スキル名 or CLAUDE.md]
- **問題**: （何が起きたか）
- **原因**: （なぜ起きたか）
- **提案**: （具体的な改善内容）
```

重要: 提案はピンポイントな対処ではなく、汎用的・再利用可能な観点で行うこと。

### 5. ユーザーとの対話

- 改善案についてユーザーの意見を聞く
- 合意した改善のみ実施する（スキル更新、CLAUDE.md 更新等）
- 実施した場合はコミット・プッシュ・PR 作成まで行う
